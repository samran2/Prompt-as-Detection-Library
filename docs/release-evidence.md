# Release Evidence

## Principle

A release claim is valid only when it points to evidence for the exact commit and
artifact being released. Passing checks on another branch, a rebuilt archive with
different bytes, or a screenshot without an artifact hash is not equivalent.

The current project is a development build and live demo, not a stable v1.0
release. Existing CI and preview archives are useful inputs but do not yet prove all
gates below.

## Evidence bundle

Each release candidate produces one immutable evidence bundle containing:

- release version, tag, commit SHA, source date, and build-environment identity;
- source provenance manifest and all pinned ATT&CK 19.2 input hashes;
- schema validation, migration, generated-content, CLI, browser, and fixture results;
- human review and lab-validation coverage summaries derived from record hashes;
- accessibility and performance evidence for the exact workbench artifact;
- dependency lockfiles, license inventory, vulnerability and secret-scan results;
- SPDX or CycloneDX SBOM for each distributed artifact and OCI image;
- SHA-256 checksums for archives, site bundle, manifests, and container digest;
- Sigstore signature or attestation verification material;
- SLSA Build L2 or higher provenance identifying builder, inputs, and outputs;
- deployment approval, rollback target, recovery rehearsal, and known limitations.

Evidence must be machine-readable where a standard exists and accompanied by a
short human-readable index. Sensitive findings, credentials, private logs, and
unredacted field data never enter a public bundle.

## Gate ownership

| Gate | Required proof | Release effect |
| --- | --- | --- |
| Source | Pinned source identity, hashes, license, deterministic rebuild | Missing or mismatched proof blocks release. |
| Content | 918 current prompt hashes, two reviews each, rubric thresholds | Incomplete stable-v1.0 coverage blocks release. |
| Rules | Support matrices, parser results, fixtures, observed lab outcomes | Unsupported cells remain explicit; false coverage blocks release. |
| Security | Code review, CodeQL, dependency review, secret and container scans, threat-model review | Unresolved critical/high reachable risk blocks release. |
| Accessibility | Independent WCAG 2.2 AA audit plus manual VoiceOver/NVDA record | Critical/serious barriers block stable release. |
| Supply chain | Locked build, SBOM, checksums, signatures, SLSA provenance | Missing artifact identity or provenance blocks release. |
| Operations | Deployment approval, monitoring readiness, rollback rehearsal | Production/API deployment is not allowed without it. |

## Reproducible build procedure

The release workflow checks out the immutable tag with persisted credentials
disabled, installs only locked and reviewed tooling, verifies generated bytes,
runs all required tests, and creates artifacts in a clean environment. The workflow
must not rewrite source or generated library files to make them pass.

A second clean build compares artifact hashes. Where archive metadata prevents
byte-for-byte output, the build documents the remaining source of variance and
compares normalized contents; this is an exception requiring approval, not a silent
substitute for reproducibility.

## Signing and provenance

Checksums identify bytes but do not identify the producer. Release artifacts use
keyless Sigstore signing from a protected GitHub Actions identity. Verification
instructions pin the expected repository, workflow, ref, and issuer. OCI artifacts
are addressed by digest, never only by a mutable tag.

The provenance statement is generated by the trusted build workflow, not by a
developer workstation. Workflow actions are pinned to full commit SHAs and receive
minimum permissions. Stable tags are immutable and force-push or deletion is
blocked by repository rules.

## Publication and rollback

1. Confirm the evidence bundle refers to the intended commit and all gates pass.
2. Obtain the required content, security, accessibility, and release approvals.
3. Create the immutable tag and signed release through the protected workflow.
4. Verify downloaded artifacts, signatures, attestations, and live version markers.
5. Retain the previous known-good deployment and rehearse rollback before launch.
6. If integrity, privacy, or safety evidence is invalidated, stop publication,
   restore the known-good version, preserve investigation evidence, and publish a
   clear correction.

The manual preview workflow described in [publishing](publishing.md) remains a
development aid. It must not be represented as a stable signed release.
