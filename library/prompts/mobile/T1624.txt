T1624 — Event Triggered Execution | Mobile | ATT&CK 19.2 reference
Source: https://attack.mitre.org/techniques/T1624
Source tactics: Persistence
Technique platforms: Android

Task: Propose detection logic, required telemetry, false positives, and bounded test cases.
Output target: Platform-neutral. This is an output instruction, not a verified integration.

Behavior to investigate: Adversaries may establish persistence using system mechanisms that trigger execution based on specific events. Mobile operating systems have means to subscribe to events such as receiving an SMS message, device boot completion, or other device activities. 

Adversaries may abuse these mechanisms as a means of maintaining persistent access to a victim via automatically and repeatedly executing malicious code. After gaining access to a victim’s system, adversaries may create or modify event triggers to point to malicious content that will be executed whenever the event trigger is invoked. 
Suggested telemetry (confirm availability): MobileEDR:telemetry; channel: Application registers broadcast receiver, WorkManager job, JobScheduler task, or intent filter tied to system event such as BOOT_COMPLETED, SMS_RECEIVED, CONNECTIVITY_CHANGE during persistence setup phase; data component: OS API Execution; MobileEDR:telemetry; channel: System event occurs (e.g., SMS received, device boot completed, network state changed) acting as trigger event for execution phase; data component: Application State.
Benign activity to consider: Local-baseline guidance (not a source finding): establish approved activity, expected accounts, assets, schedules and change windows for this behavior. Review source tuning variables; require local evidence before making exclusions.

AN1727 — Analytic 1727
The defender correlates application registration for system event triggers (e.g., broadcast receivers, WorkManager, JobScheduler, SMS/BOOT events) with subsequent execution of application code immediately following the triggering event, without direct user interaction. Confidence increases when execution occurs in background or locked state, is tied to sensitive triggers (SMS received, boot completed, connectivity change), and produces follow-on file or network activity inconsistent with the application’s expected role.
